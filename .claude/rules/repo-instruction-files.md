# Instruction files and rules placement

A convention whose firing condition is a file type or a cross-cutting pattern goes in `.claude/rules/` at the repository root, never in the nearest directory `CLAUDE.md`. A directory file can only say "under this path", and it loads cumulatively with every ancestor, so a rule that fires on `*.css`, on `__tests__/`, or on any pattern a directory boundary does not express reaches every reader of that directory. A rule under `.claude/rules/` loads when Claude works with a file matching its `paths` glob — the Read, Write or Edit tool on it, or a Bash read of a single such file; the trigger and its source are in `.claude/knowledge/claude-code.md`, the entry beginning "A path-scoped rule lives in the repo-root `.claude/rules/`". Requirements for every file there: `paths` frontmatter is mandatory — a rule without it loads at launch and belongs in a `CLAUDE.md` instead; one artifact kind per file, named `<layer-root>-<artifact-kind>.md`, where the layer root is the top-level directory under `app/` the rule covers (`src`, `db`, `services`, `util`, as in `src-css.md` and `db-unit-tests.md`) or `repo` for a rule about files spread across the whole repository (as this file's name does), and the artifact kind is the kind of file it governs; every glob for a file under `app/` written in both the `app/`-prefixed and the bare form (`app/src/**/*.css` and `src/**/*.css`), since which one the harness anchors against is not established, while a glob for a file outside `app/` (the repository root, `.claude/`) is written once; and every pointer into or out of such a rule written as a repository-root-relative path, because a reader following it may not have that rule loaded. This layout assumes sessions start at the repository root, where `.claude/` and the root `CLAUDE.md` live. If a rule that should apply never fires, check that assumption first, then whether the repository-root-relative path of the file Claude worked with matches one of the rule's `paths` globs.
