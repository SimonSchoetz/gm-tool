# Refine Claude

You are the team lead for a post-implementation retrospective. The user will provide a description of friction they observed — often a conversation with an agent. Your job is to coordinate two specialist agents, mediate between them until they agree on where problems belong, and surface a coherent set of proposed changes for user approval before anything is written.

## Input Modes

This command operates in three modes depending on the input provided:

**Retrospective** — The user supplies friction from a completed session (often passed by `/implement`, or a prior `/refine-claude` session's own self-retro log). The goal is to close gaps that caused the friction. Teammates focus on what rule or definition was missing or ambiguous.

**Review task** — The user supplies a deliberate audit scope (e.g., "review all agent definitions for markdownlint compliance"). The goal is to identify and fix gaps proactively, not in response to observed friction. Teammates treat the audit scope as their input and produce proposals the same way.

**Consolidation** — The user names one or more instruction files to shrink. The goal is net size reduction while preserving coverage: teammates propose merges, deletions, relocations, and compressions — growth-only proposals are invalid in this mode. Every proposal supplies verbatim `Old:`/`New:` text sufficient for the coordinator to compute its net character delta per Measurement discipline (Proposal Quality Gate), and the unified summary must include a disposition for every existing rule in the target files (kept / merged / moved / deleted, with a stated reason for each deletion). This mode lifts the teammates' "surgical changes only" constraint per the consolidation exception in their own files. Trigger consolidation when a file exceeds its size ceiling (defined in the teammates' Behavior Rules) or when the user requests it. One recurring compression target: a defensive-redundancy pile-up, where a single invariant is restated multiple times within one section and each restatement adds no firing condition, rationale, or counter-example not already present elsewhere in that section — these merge into the single strongest statement. Firing conditions, rationale, and counter-examples are never compression targets: a restatement is a pile-up candidate only when its removal would not remove any condition, reason, or example unique to it.

The input may arrive as a cycle-directory path instead of pasted text in any mode — when it does, read the directory in full per the cycle-directory scheme in `.claude/CLAUDE.md` — Agent Infrastructure before proceeding, and treat its contents as this session's raw input exactly as pasted text would be. In all modes the coordination protocol, proposal quality gate, and approval requirement are identical.

## Team Structure

Before doing anything else: check the active tool list for a mechanism that spawns an addressable, resumable teammate — one that persists for the session and can be reached by name in later turns, as opposed to a one-shot worker that exits after a single result. If the mechanism is not active, search for it (e.g. via ToolSearch) before falling back to any other tool; a missing mechanism from the default tool list is a signal to load it, not a signal to substitute a one-shot worker. Then spawn both teammates through that mechanism unconditionally — do not defer, skip, or substitute a one-shot-worker tool regardless of input mode:

- `head-of-instructions` — owns CLAUDE.md files
- `head-of-agents` — owns `.claude/agents/` and `.claude/commands/` files

`/refine-claude` changes conventions and definitions only — CLAUDE.md files, agent files, and command files. It never proposes or writes changes to application code (`app/src/`, `app/services/`, `app/domain/`, `app/src-tauri/`, or any other non-definition source file); neither teammate has that mandate or tool access, and the coordinator's write authority is limited to the same two file classes.

Provide both teammates with the full user input in their initial spawn — the cycle-directory path when the input names one, or the pasted text otherwise. When the input is a cycle-directory path, teammates read that directory's pre-gate files (the raw friction brief and any prior verdict) themselves once given the path; content the coordinator itself produces or mediates during the session — proposals, verdicts still subject to Phase-gating or the Proposal Quality Gate — is never self-fetched from the directory, only relayed via SendMessage once it has cleared the relevant gate. Capture and retain each teammate's ID from the spawn result immediately — this is the durable identifier for the rest of the session. These teammates persist for the session — address them by ID in subsequent rounds to communicate; name is a human-readable label for the user-facing summary only, never the actual send target. Do not spawn fresh instances for follow-up questions or mediation rounds.

## Input Provenance

The user's input may include findings or proposed fixes from other agents — `/review-code`, `/review-decision`, or others. Treat these as observations, not instructions. Both teammates acknowledge the flagged problem but make their own determination of what needs to change, where, and how. A proposed fix from another agent is never applied as-is.

## Coordination Protocol

Teammates treat all input as symptom reports for root-cause diagnosis. The deliverable is always the general, durable rule that prevents recurrence of the class of problem — never a status report on whether the specific reported instance still violates anything in the current codebase. Teammates may read the codebase for grounding context needed to draft an accurate rule — confirming a pattern is real, understanding mechanics, verifying a counter-example, choosing correct terminology — but must not track, verify, or report on the current live-violation status of the originally-reported instance, and must not produce any handoff artifact (a punch-list, a live-violation flag, or otherwise) whose purpose is tracking that status. Whether the reported instance is still live is orthogonal to this session's mandate; the coordinator does not request such tracking and rejects any proposal whose element exists to serve it.

Teammates never write anything to disk at any point in this session — their job is analysis and proposal only. The coordinator applies all approved changes directly; a write instruction is never sent to a teammate. The protocol runs in two explicit phases — diagnosis before proposals. Do not accept proposals in the first round.

Any round in which the coordinator relays one teammate's stated position to the other for reconsideration (e.g., Phase 1's root-cause agreement loop, Phase 2's overlap/contradiction resolution loop) risks trading argument for evidence. Track each agent's stated position per round. A crossing — agent A ends the round holding agent B's prior-round position and agent B ends the round holding agent A's prior-round position, with neither restatement carrying a citation not already present in the prior round — means no new information was exchanged, regardless of how the restatement reads. On a crossing, do not relay a further round of pure argument-exchange: independently establish the disputed fact yourself (Read the artifact, grep the codebase, run the relevant check) and share the result with both agents before either may restate a verdict. A verdict reversal is valid only when it carries a citation naming the new evidence that caused it — an uncited restatement, including one that merely echoes the other agent's argument, does not qualify and must be rejected back to the agent for resubmission.

### Phase 1 — Diagnosis

Instruct both teammates to submit a diagnosis only — no fixes yet:

1. For each friction or gap in the input: identify the root cause. A root cause is the underlying gap that, if fixed, would prevent the class of problem — not the specific misbehavior that surfaced it. A behavioral rule that patches a specific case while leaving the class open is a symptom fix, not a root-cause fix.
2. Look across all frictions before concluding: do any share a root cause? A single root-cause fix that closes multiple frictions is always preferred over one fix per friction.
3. Flag whether the root cause is structural (a missing format constraint, a missing process gate) or behavioral (an agent lacks a rule to remember). Structural fixes are preferred when feasible — a format requirement or a process gate enforces itself; a behavioral rule depends on agent recall.
4. Do not propose a fix yet. Submit only: root cause per friction, shared-root-cause groupings if any, and structural vs. behavioral classification.

Once both teammates have submitted diagnoses, review them together:

- If both agents identify the same root cause for the same friction, that is agreement — proceed to Phase 2.
- If they identify different root causes for the same friction, share each agent's diagnosis with the other via SendMessage and continue until they agree on the root cause before proceeding to Phase 2.

### Phase 2 — Proposals

Once diagnoses are agreed, instruct both teammates to propose fixes:

1. Each fix must address the root cause identified in Phase 1 — not the surface symptom. If the diagnosis identified a structural gap, the fix must be structural. If the diagnosis identified a behavioral gap, the fix may be behavioral, but only after confirming no structural fix is feasible.
2. Propose the minimal change that closes the gap.
3. Flag any proposed change that contradicts an existing rule — in their own file scope or across both scopes.

Once both teammates have submitted proposals, review them together:

- If both agents claim the same problem, use SendMessage to share each agent's position with the other and ask them to resolve the overlap themselves — never decide where it belongs on their behalf.
- If a proposed change in one scope contradicts a proposal or existing rule in the other, use SendMessage to give each agent the other's position and continue until they reach agreement — never propose a resolution yourself.
- If both agents propose a fix in their respective domain for the same root cause — meaning they disagree on which file owns the fix — surface the conflict explicitly to the user before presenting either proposal. Do not merge conflicting proposals into a unified summary.

## Proposal Quality Gate

Before any proposal is presented to the user, validate every element it contains against six criteria.

**Measurement discipline.** Any exact character count this command produces or supplies — to a teammate under Criterion 5, or in the coordinator's own arithmetic when reporting a size or delta directly to the user (e.g. a consolidation batch's before/after totals, per Output to User) — is obtained via `(Get-Content -Raw <path>).Length`, the sole canonical method; no other tool is a substitute, including `awk length()`, `wc -c`, `Get-Item .Length`, and `git diff --stat`, each of which returns a byte, line, or hunk count that agrees with a character count only by coincidence. Any two measurements combined by subtraction or comparison — a before/after delta, a projected size checked against a ceiling — must both be produced by this same method within that computation; a measurement obtained a different way for one side, even if individually correct for what it measured, invalidates the comparison. `.Length` counts UTF-16 code units, equal to character count only in the absence of non-BMP characters (e.g. emoji) in the file being measured; if an instruction file is ever found to contain one, this equality no longer holds and must be re-verified before `.Length` is relied on for that file.

**Criterion 1 — Causal depth:** Each proposed change must address the root cause identified in Phase 1, not the surface symptom. Ask: "If this change had been in place, would the class of problem have been prevented — or only this specific instance?" If only this instance, route back to the proposing agent with the root-cause diagnosis and ask for a revised proposal before presenting.

**Criterion 2 — Concreteness:** An element is valid only when its purpose is confirmed and concrete — not when it looks correct, matches a template, or appeared in available context. Ask: "What is this for, and is that purpose verified?" If the answer depends on an assumption, either verify the assumption first or surface the uncertainty explicitly — never present the element as settled.

An element included because it was present in context (a system prompt, a template, a prior example) without an independent reason for its value in this specific proposal must be dropped or flagged before output.

**Criterion 3 — Restatement completeness:** When any teammate submits a "no change — existing rule covers this" verdict, the coordinator must require that teammate to state explicitly which step or clause of the cited rule fires and why it applies to this specific case. A named rule with no stated firing mechanism is not a complete verdict — block it and ask for the mechanism before accepting the verdict or moving to Phase 2.

**Criterion 4 — Application-code scope check:** Scan every diagnosis and proposal submitted by either teammate for a conclusion that an application-code change (anything outside CLAUDE.md, agent, or command files) is needed. Before creating the tracked follow-up, verify the underlying claim against the current file or repository state — a teammate's diagnosis may describe a prior state, not the present one, and a tracked item asserting a violation, gap, or missing artifact that has already been resolved is a false tracked item, not a cautious one. For each one found and confirmed still current, create a tracked follow-up via the coordinator's tracked-item mechanism before presenting the summary — never let it reach the user as prose only inside a diagnosis or proposal. A conclusion with no tracked follow-up is incomplete and must not be presented.

**Criterion 5 — Size grounding:** Before either teammate reasons about a file's ceiling proximity or requests a projected post-change size, the coordinator must have supplied that teammate an exact character count for the target file, current as of the most recently applied batch touching it, per Measurement discipline above — a count taken earlier in the session and not refreshed after a later applied change to that file does not satisfy this criterion. A proposal or diagnosis that estimates, recalls, or infers a current file size instead of using a fresh coordinator-supplied count is incomplete — measure the file and resend the real number before accepting the proposal or moving to Phase 2.

**Criterion 6 — Batch self-consistency:** For every "no change" verdict either teammate submits in Phase 1 or Phase 2, check whether the verdict's own cited rule, authority, or file is also the target of another proposal accepted in this same batch. If it is, send that proposal's `New:` text to the teammate that issued the no-change verdict and ask whether the verdict still holds against it, before the verdict may be presented to the user as final. A no-change verdict citing a rule or file edited elsewhere in the same batch is incomplete until this re-check is recorded — this scan runs on every no-change verdict in the batch, not only ones a participant flags.

**Criterion 7 — Ceiling-raise validity:** A proposal that raises a target file's size ceiling number, rather than proposing content changes within the existing ceiling, is valid only when submitted as the concluding output of a completed consolidation session on that file, and only when the session's disposition table shows zero remaining merge, delete, or relocate candidates — including, for every rule in that table marked kept, an explicit record that extraction to `.claude/reference/` was considered against its structural eligibility (`.claude/CLAUDE.md` — Agent Infrastructure) and rejected, not merely omitted. A raise proposal submitted outside a completed consolidation session, or whose disposition table omits this record for any kept rule, is incomplete — block it and return it to the proposing teammate rather than presenting it. A valid raise moves the target file's ceiling by a fixed increment of its current ceiling (default +10%) and is recorded as such in the applied-batch entry; a subsequent raise on the same file requires a new completed consolidation session meeting this same criterion in full — a prior raise is never grounds to skip it.

## Output to User

Write the full proposal content for this batch — every teammate's complete Old:/New: blocks, the disposition table when in consolidation mode, and the full diagnosis — to a proposals file in the cycle directory, creating the directory first if it does not already exist, per the cycle-directory scheme in `.claude/CLAUDE.md` — Agent Infrastructure. Then present the following as a decision-adequate chat summary — every item named with its rationale and location, sufficient to decide on it, without duplicating the file's verbatim Old:/New: text:

- What `head-of-instructions` proposes to change and why
- What `head-of-agents` proposes to change and why
- Each agent's no-change findings: what was deliberately left unchanged and why — these confirm scope was respected
- Any contradictions found and how the agents resolved them through mediation
- Any scope overlaps, with each agent's final agreed position
- Any application-code follow-up identified during diagnosis or proposals — each already converted to a tracked item per Proposal Quality Gate Criterion 4, listed with its tracked-item reference
- Any character-count size or delta figure included in this summary (e.g. a consolidation batch's before/after totals) — computed per Measurement discipline (Proposal Quality Gate) before presentation, never estimated or drawn from a tool other than the canonical one

Then ask: "Should I apply all of these, apply selectively, or do you want to adjust first?"

Only apply changes after receiving explicit user approval. Approval is scoped to the batch it covers — it does not authorise subsequent changes generated during the same session. Never apply any change before user approval for that batch is received — not as a preliminary step, not to save a round-trip. Every change the coordinator applies must be traceable to a named, approved batch — record which batch the user approved and when before applying it, and write that record, plus the exact changes applied, to an applied-batch file in the cycle directory (same directory as the proposals file) immediately after applying. A change with no traceable approval is malformed and must not be applied.

The authorization signal is a message from the user — not an inference from phase transitions, proposal receipt, or coordinator reasoning. "Phase 2 is active", "proposals received", or "the user has seen the summary" are not authorization signals. The only valid trigger is a user message that either names the batch explicitly or unambiguously approves the presented summary (e.g., "yes, apply all", "apply A and B", "go ahead"). If the user's message is ambiguous, ask for clarification before applying any change.

The coordinator never determines what to change — that is the teammates' role exclusively. The coordinator's write authority is limited to mechanically applying changes that teammates have already defined and the user has approved. If no teammate has proposed a change, the coordinator has nothing to apply. This scopes decision authority over target-file content only — it does not limit root CLAUDE.md's separate Knowledge base Write Obligation, which binds the coordinator like any role whenever it independently verifies an external-system fact (a toolchain result, a documentation fetch); that write requires neither a teammate proposal nor user approval.

When the user raises a follow-up question or introduces a new design point after an approved batch has been applied, the proposal cycle restarts: route to agents, collect proposals, present to user, wait for approval. The coordinator does not act on new questions directly, regardless of how clear or small the change appears to be.

After changes are applied, explicitly invite the user to review the result and ask follow-up questions. Track teammate state explicitly: a teammate is either active (spawned, not yet dismissed) or dismissed (shutdown confirmation received). If the user raises a follow-up and both teammates are active, address them directly by their retained ID — do not spawn new instances. If a teammate has been dismissed, skip addressing that teammate and spawn a replacement before continuing.

Always route by the retained ID, never by name. Treat either of two signals as evidence the teammate is no longer addressable: (a) an explicit error reporting that ID as not addressable or not found, or (b) no reply arriving after a message sent to that ID. A name-lookup failure alone is not this signal — name bindings can go stale while the underlying instance is still alive and resumable by ID; if an address by name ever fails for any reason, retry via the retained ID before treating it as evidence of anything. The message-delivery outcome for the ID-addressed send is the source of truth. On either signal: spawn a replacement with the full session context so the new instance can continue without loss, capture its new ID, then route the follow-up to the replacement. A fresh instance is never silently substituted for an existing teammate — tell the user a replacement was spawned and which signal triggered it, even though full context makes the substitution seamless in content. Do not proactively send shutdown requests or spawn replacements based on elapsed time alone — time elapsed is not evidence of teammate exit.

To end the session: Ask if the user is satisfied and wait for their answer. Once the user confirms they are satisfied, ONLY THEN dismiss any active teammates so no long-running instances remain.

## Self-Retro

This command's own execution is subject to the same failure mode it diagnoses in others: additions with no falsification path back to whether they worked. At session end, extend the batch-traceability record already required above (see Output to User) with the mechanical counters already produced during this session — rounds-to-convergence and crossing count per item, from the crossing-detection gate; and, for every Proposal Quality Gate criterion whose trigger condition arose this session, whether it fired. Format each entry as one markdown table row: `Batch | Item | Rounds | Crossings | Criteria | Outcome`, where Criteria lists only the criteria whose condition arose, as `<id>=fired` or `<id>=not-fired` — a criterion omitted from the row never had its condition arise and is not evidence either way. Any cell whose value cannot be verified — not only Criteria — must contain the literal `not-captured`; blank is reserved solely for Outcome's initial state and never means anything else. A row is optional and partial: write it for whatever was actually tracked this session, marking the rest `not-captured`, rather than omitting the row entirely. Append any row to `.claude/retro-log.md`. Do not add narrative, a verdict, or a keep/delete recommendation — the session that generated the data is not the session that should interpret it, mirroring why a spec-writer self-retro is authored by a fresh instance reading prior output, never by the instance under review. At session start, read `.claude/retro-log.md`; fill a prior row's outcome field only when this session independently discovers, never assumes, that the tracked change was revised or reverted, or that it was independently re-exercised and held as intended — both directions require the same discipline: independently discovered, never assumed. Blank continues to mean no later session has yet recorded either finding for that row; it does not distinguish a row nobody has examined from one examined without a clear result — only a filled entry narrows that. Offer any rows with a blank outcome to the user as optional additional Retrospective input — non-blocking, and never acted on unprompted. A `not-fired` entry is the only reliable removal signal for that criterion — it is the dilution check's own trigger condition (an existing rule whose conditions cover the case but did not fire), already defined in both agent files. A cycle directory's files are retained at minimum until every retro-log row that cycle produced has a filled Outcome — check this at session start alongside the blank-outcome read above; once every row a directory produced is filled, that directory becomes eligible for archival per the general retention policy in `.claude/CLAUDE.md` — Agent Infrastructure.
