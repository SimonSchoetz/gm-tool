# Spec quality brief — `app/docs/SPEC_SECURITY_HARDENING.md`

Produced by an `/implement` session on branch `docs/security-audit-sync-channel`. The spec used the split format: a root index carrying the progress tracker, nine Key Architectural Decisions, and the CLAUDE.md impact section, plus six sub-feature files. All six sub-features were implemented and committed; the review loop ran one cycle and exited on an architect no-violations verdict.

## Over-specified

**SF6 reproduced the entire body of the file it creates.** `app/docs/SPEC_SECURITY_HARDENING_SF6.md` contains a fenced block holding the complete ~40-line text of `app/docs/security-audit-round-2-scope.md`, which the implementer then wrote out verbatim. Not one line of it encodes a decision the implementer could get wrong: the four audit areas, their read lists, and their questions are content, and the file has no imports, no types, and no call sites. `app/docs/CLAUDE.md` names this case directly — a spec "must carry decisions, not derivations" and must not reproduce "a prose paragraph that narrates the implementation step by step." The decision content in SF6 is roughly three sentences: which four areas carry forward, that the trust model is restated rather than re-derived, and that the document is deleted on the fix spec's completion. Everything else is authoring, which is what the implementer is for.

**SF1's test section restated scaffolding the implementer reads from the file anyway.** It describes the existing mock setup in `app/db/__tests__/mention-search.test.ts` — the module-scope `vi.mock`, the static top-level import, the `vi.resetModules()` in `afterEach` — explains why that pattern is correct for this file, and concludes "Keep the scaffolding as it is." The implementer opens the file to add tests to it and sees all of this. The load-bearing instruction is the last four words.

**SF4 pre-verified every existing fixture against the new parse in prose.** A paragraph walks through `NPC_ROW`'s four columns against `npcTable.zodSchema`'s declarations, then the `table_config` fixture's three, then notes that the two tests passing `id: undefined` return before reaching the parse. The analysis is correct and it did predict the outcome — the suite went 661 to 668 passing with no regressions. But `npx vitest run` establishes the same fact in twenty seconds, and the paragraph's cost is that a reader cannot tell it from a specification of required behavior.

## Under-specified or wrong

**SF5's Verification section states a precondition no implementing agent in this harness can satisfy, and never says who performs it.** It reads "Both passes are required before this sub-feature is committed" and specifies six checks to be observed "with the webview devtools console open." A Tauri app renders in a native OS webview; the implementing agent's browser tooling drives a separate in-app browser and cannot attach to it. Written in the imperative with no actor named, the requirement reads as an implementer obligation, and the session stalled on it until the user chose a disposition. What the spec should have said: name the human as the actor for both passes, and state what the implementer can verify unaided — that `tauri build` deserializes `tauri.conf.json` at compile time, so a successful release build proves the `csp` and `devCsp` shapes are accepted and the compile-time hash and nonce rewriting did not fail, while proving nothing about the six runtime behaviors. This is the one gap in the spec that cost the session a blocking question.

**SF2's stated rationale for the inline format-argument form is factually wrong.** It directs `format!("Invalid image id: {id}")` over `format!("...: {}", id)` "because that is the form `clippy::uninlined_format_args` prefers and `cargo clippy -- -D warnings` is a required gate whenever `src-tauri/` is touched." That lint is not active in this configuration. The baseline `cargo clippy -- -D warnings` run at session start passed against the pre-existing `format!("Invalid file extension: {}", extension)` calls sitting in the very files SF2 modifies, and there is no `clippy.toml` and no lint configuration in `Cargo.toml`. The instruction was followed and the code is fine — the inline form is the better one and costs nothing — but the reason given for it does not hold, and a rationale that names a gate as forcing a choice invites the implementer to treat the gate as verification that the choice was necessary.

**SF2 directs a `use super::{VALID_EXTENSIONS, is_valid_image_id};` name order without stating that rustfmt determines it.** The order given is correct — `cargo fmt --check` passes — but an implementer who reversed the two names for readability would fail the gate and have to discover why. One clause naming rustfmt's sort as the reason would remove that.

## Decisions vs. substitutions

- **SF1** — mixed. Decisions: that the load-bearing guard belongs at the interpolation site rather than the service layer; that each guard returns the function's own empty result (`[]`, `null`) rather than throwing, because `searchByName` runs on every keystroke behind the typeahead; that `table_config` gates on `SYNCED_TABLE_NAMES` while mention-search gates on `ENTITY_TYPES`, and why those two lists must not be conflated; that the `tableName === ''` check is dropped rather than kept, since `SYNCED_TABLE_NAMES.includes('')` is already false. Substitutions: the exact comment text, the two rejection test bodies, and the stale-fixture rewrite from `places` to `adventures`.
- **SF2** — mixed. Decisions: the character-class-only design with no length constraint, and its reasoning that a string over nanoid's URL-safe alphabet cannot contain a separator regardless of length; that the Rust check is the trust boundary and the Zod regex is not a substitute for it; that `IMAGE_ID_REGEX` stays module-private because it has exactly one consumer; that `extension` stays a bare `z.string()` rather than duplicating `VALID_EXTENSIONS`. Substitutions: applying the identical three-line guard to six files, and the two rejection tests.
- **SF3** — decision throughout. The `HashMap<EndpointId, u8>` on `PairingSession` rather than on the candidate, the removal of the `match` fallback that resolved a missing candidate to `MAX_CODE_FAILURES`, the explicit instruction *not* to remove the `code_failures` entry in the limit-reached branch, and the borrow-sequence argument for why the inner block's mutable borrow ends before the branch takes its own. None of it is derivable from the surrounding code.
- **SF4** — mixed, weighted to decision. Decisions: the `syncedTable` helper as the way to remove a twelve-fold repeated expression rather than appending a field to twelve literals; the bare `z.ZodObject` annotation, carrying a toolchain citation for why the concrete parameterized type is assignable to it; `.partial()` over the schema as authored, because a peer on a different schema version legitimately omits columns and rejecting those rows would be a data-loss bug; passing `filtered` rather than the parse output onward; the `#[cfg(unix)]` gate as a scoping decision rather than an unfinished port. Substitutions: the twelve helper call lines and the two test bodies.
- **SF5** — decision throughout. Every directive carries a stated reason, and two of them are the kind an implementer would get wrong unaided: `img-src` naming both `asset:` and `http://asset.localhost` because `convertFileSrc()` resolves differently per platform and omitting either breaks images on one family only — on the family this project does not develop on — and `connect-src` naming `ipc:` and `http://ipc.localhost` because every `invoke` and every `plugin-sql` query travels that origin, so omitting it disables the application rather than degrading it.
- **SF6** — substitution. The new file's entire body was supplied verbatim; the deletion is one command.

## Format observations

**The split format held up.** The root index's nine Key Architectural Decisions carried every rationale the sub-features needed, and no sub-feature required an inline self-containment note because each restated its own reason at the decision site. The "no Foundation SF" claim was accurate: SF1 and SF4 both modify `app/db/_sync/apply-upsert.ts`, and each committed independently with `tsc --noEmit` clean, exactly as the tracker predicted.

**A Verification section needs a "performed by" field.** SF5 is the only sub-feature here whose verification is not a toolchain invocation, and it is the only one that stalled. A verification step that a human must perform is structurally different from one the implementer runs, and the spec format currently has no way to mark the difference — so the distinction has to be inferred from the content, which is exactly what failed.

**Manual-verification markers are specified in two incompatible shapes.** `app/docs/CLAUDE.md` describes `[MANUAL-VERIFY]` as a bracketed literal that "a downstream scan can find deterministically," and `/implement`'s post-loop scan greps the spec files for that literal. SF3 instead directed an unbracketed `// MANUAL-VERIFY:` comment placed in Rust source. Both markers are reasonable in isolation; together they mean the scan reported clean on a branch that has a real untested interaction — the pairing reconnect scenario — which reached the user only because it was noticed while reading SF3. Either the scan must match the source-file form too, or a spec placing a marker in source must also place the bracketed literal in the spec file.
