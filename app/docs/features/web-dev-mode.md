# Web development mode

**Purpose.** `pnpm run web` from `app/`, or the `web` launch configuration in the desktop app, runs the app in a plain browser against a copy of the installed release app's data, so that an agent session or the developer can verify UI acceptance criteria in the browser pane instead of by hand. Every Tauri call goes through one platform module, which answers from Tauri in the app and from the dev data server inside Vite in web mode; only what needs the native host — the native file dialog, sync between devices, the updater, the backup — stays a hand test in the Tauri app.

**Users.** The developer and the agent sessions working in this checkout, not the GM: web mode is a development tool and never reaches a release build.

## How it works

Happy path:

1. `pnpm run web` (or `preview_start` with the `web` configuration, which runs that script on port 5173) starts Vite in mode `web`. Before Vite accepts requests, the dev data server plugin finds the installed release app's data under `~/Library/Application Support/com.gm-tool/`, copies its database and images into a temporary folder (`gm-tool-web-mode` under the OS temp directory, emptied at every start), runs the checkout's pending migrations on the copy, and registers its routes under `/__dev-data` on Vite's own origin.
2. The browser loads the app. The platform module's web implementation confirms the server with a health request, then every database statement and every Tauri command the app makes is posted to the server, which answers from the copy. The first page shows the adventure list with the installed app's adventures and their images, without a reload.
3. Every screen the sidebar and the lists reach renders from the copy. Creating, editing with auto-save, duplicating, pinning and deleting write to the copy; a page reload shows them still there; restarting the server starts again from the installed app's current data.
4. The image upload and replace buttons take the next of three committed fixture images in file-name order — a landscape PNG, a portrait JPEG, a square WebP — instead of opening a dialog; the entity shows the image, served from the copy, and the framing dialog works on it.
5. Settings shows the checkout's `package.json` version as the current version and no update; the mirrored paired devices are listed and disconnected, and no peer ever connects. Entering pairing mode asks the server, which answers a fixed code.
6. An embedded link opens in a new browser tab when its URL is `http:`, `https:`, `mailto:` or `tel:`.

Failure:

- No installed app on the machine, or a machine that is not macOS: Vite does not start, and the error names the expected database path (`~/Library/Application Support/com.gm-tool/gm_tool.db`) or the macOS-only path.
- Vite started with a `server.host` other than `false` or `localhost`: the plugin refuses to start, naming the host.
- The dev data server not answering its health route — a plain `vite` without web mode, or a server gone away before a reload: the Error Boundary shows a message naming the `web` launch configuration and `pnpm run web` as the way to start it.
- A request that fails the guard is answered with an error the app's own domain errors carry: a `Host` other than the loopback names (403), a POST without `application/json` (415), a body over 64 MB (413), a body of the wrong shape, an image name outside `<id>.<extension>` or an upload path that is not a fixture (400). A command web mode cannot answer — downloading or installing an update, the three backup commands, an unknown command — rejects with a message naming web mode.
- An embedded link of another scheme (`javascript:`, `file:`, …) is refused with an error naming the scheme; the editor's "Open in browser" does not catch it, so it surfaces as an unhandled rejection (see Open points).
- A release build and the Tauri app (`pnpm run dev`) carry none of this: the build contains neither the server routes nor the web implementation, and `pnpm run dev` starts Vite alone through `dev:frontend`.

Where the user waits: at server start, for the copy (a 1.3 MB database and 24 MB of images at the time of writing) and the migrations, before Vite accepts requests; on the first page load, for one health request before the database is used. Saving never holds up typing, as in the app.

## Data

- **Reads:** the installed release app's database file and `images/` directory under `~/Library/Application Support/com.gm-tool/` (the identifier from `tauri.conf.json`), once per server start; the checkout's migrations; the `version` of `package.json`; the three fixture images.
- **Writes:** only the temporary copy — its database (a `-wal` file beside it while the server holds it open), its `_migrations` ledger as the pending migrations run, and its `images/`, where uploads and replacements land. Nothing under the installed app's directory is created, changed or removed, with one exception: a database the release app left with a `-wal` file beside it is recovered in place when the copy step opens and closes it, as the app's next launch would do.
- **Never:** nothing is committed, nothing reaches a paired device, and web-mode edits do not survive a server restart.

## Open points

None in the open-questions register.

Not yet registered, each from the implementer's handoff; the lead takes them to the user:

- In web mode the pairing code is answered by the server but never shown: the pairing dialog shows it only after a peer requests it, and no peer exists in web mode. The settings rule above depends on it.
- The unreachable-server rule above cannot be observed by stopping the server and reloading: the server is Vite's own process, so a reload then fails at the connection and no page can show the Error Boundary; the message is reached only when a page is served without the server behind it.
- The editor's "Open in browser" does not catch a refused link, so a web-mode scheme rejection, and the Tauri opener's own scope rejection, surface as an unhandled rejection. The link rules above depend on it.
