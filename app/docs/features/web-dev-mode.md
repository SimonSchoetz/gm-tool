# Web development mode

**Purpose.** `pnpm run web` from `app/`, or the `web` launch configuration in the desktop app, runs the app in a plain browser against a copy of the Tauri dev app's data — the database `pnpm run dev` runs on, with the developer's test data in it — so that an agent session or the developer can verify UI acceptance criteria in the browser pane instead of by hand. A second variant, the seeded mode (`pnpm run web:seed`), starts instead from an empty database that the checkout's migrations build and a fixed seed fills, so a check runs against the same named data on every machine and at every start (see Seeded mode). Every Tauri call goes through one platform module, which answers from Tauri in the app and from the dev data server inside Vite in web mode; only what needs the native host — the native file dialog, sync between devices, the updater, the backup — stays a hand test in the Tauri app.

**Users.** The developer and the agent sessions working in this checkout, not the GM: web mode is a development tool and never reaches a release build.

## How it works

Happy path:

1. `pnpm run web` (or `preview_start` with the `web` configuration, which runs that script on port 5173) starts Vite in mode `web`. Before Vite accepts requests, the dev data server plugin finds the Tauri dev app's data under `~/Library/Application Support/com.gm-tool.dev/` (the identifier from `tauri.dev.conf.json`), copies its database and images into a temporary folder (`gm-tool-web-mode` under the OS temp directory, emptied at every start), runs the checkout's pending migrations on the copy, and registers its routes under `/__dev-data` on Vite's own origin.
2. The browser loads the app. The platform module's web implementation confirms the server with a health request, then every database statement and every Tauri command the app makes is posted to the server, which answers from the copy. The first page shows the adventure list with the dev app's adventures and their images, without a reload.
3. Every screen the sidebar and the lists reach renders from the copy. Creating, editing with auto-save, duplicating, pinning and deleting write to the copy; a page reload shows them still there; restarting the server starts again from the dev app's current data.
4. The image upload and replace buttons take the next of three committed fixture images in file-name order — a landscape PNG, a portrait JPEG, a square WebP — instead of opening a dialog; the entity shows the image, served from the copy, and the framing dialog works on it.
5. Settings shows the checkout's `package.json` version as the current version and no update; the mirrored paired devices are listed and disconnected, and no peer ever connects. Entering pairing mode asks the server, which answers a fixed code.
6. An embedded link opens in a new browser tab when its URL is `http:`, `https:`, `mailto:` or `tel:`.

Failure:

- No dev app database yet, or a machine that is not macOS: Vite does not start, and the error names the expected database path (`~/Library/Application Support/com.gm-tool.dev/gm_tool.db`) with `pnpm run dev` as the way to create it — run against a dev app without a database, the mirror copies the installed release app's data in without asking (`dev-data-mirror.md`) — or the macOS-only path. Web mode never falls back to the installed app's data.
- Vite started with a `server.host` other than `false` or `localhost`: the plugin refuses to start, naming the host.
- The dev data server not answering its health route with 204 — any other answer, Vite's SPA fallback included: the Error Boundary shows a message naming the `web` launch configuration and `pnpm run web` as the way to start it. A plain `vite` without web mode loads the Tauri implementation instead, so a browser on it shows plugin-sql's own error.
- A request that fails the guard is answered with an error the app's own domain errors carry: a `Host` other than the loopback names (403), a POST without `application/json` (415), a body over 64 MB (413), a body of the wrong shape, an image name outside `<id>.<extension>` or an upload path that is not a fixture (400). A command web mode cannot answer — downloading or installing an update, the three backup commands, an unknown command — rejects with a message naming web mode.
- An embedded link of another scheme (`javascript:`, `file:`, …) is refused with an error naming the scheme; the editor's "Open in browser" does not catch it, so it surfaces as an unhandled rejection (see Open points).
- A release build and the Tauri app (`pnpm run dev`) carry none of this: the build contains neither the server routes nor the web implementation, and `pnpm run dev` first runs the data mirror (`dev-data-mirror.md`), then starts Vite alone through `dev:frontend`.

## Seeded mode

`pnpm run web:seed` from `app/` or the repository root, or `preview_start` with the `seeded-web` launch configuration (port 5174), starts the same Vite web mode with `GM_TOOL_WEB_DATA=seed` set. Instead of copying the dev app's data, the dev data server creates an empty database and an empty `images/` folder in its temporary folder, runs every migration of the checkout on it, then applies the seed (`app/dev-data-server/seed/seed.ts`), whose images are copies of the fixture images in that `images/` folder, before Vite accepts requests. Everything after that — the platform module, the routes, the fixture images, settings — works as in the copy mode above. The seeded mode reads nothing under `~/Library/Application Support/`, so it also starts on a machine with no dev app data.

The seed creates every row through the app's own services, never through SQL of its own, so a change to a schema or a service signature fails `type-check` on the seed instead of leaving it stale. The services import through the project's path aliases, which Vite's config bundle cannot resolve, so the dev data server runs the seed in a short-lived Vite server of its own that resolves them, with `@platform` pointed at a module that answers `loadDatabase` with the fresh database and `invoke` from the dev data server's own command table, so the services' `save_image` copies a fixture image into the temporary `images/` folder (`seedDatabase`, `seed/seedPlatform`).

## Data

- **Reads (seeded mode):** the checkout's migrations and the seed, the `version` of `package.json`, the three fixture images, which the seed also copies; no app data directory.
- **Reads:** the Tauri dev app's database file and `images/` directory under `~/Library/Application Support/com.gm-tool.dev/` (the identifier from `tauri.dev.conf.json`), once per server start; the checkout's migrations; the `version` of `package.json`; the three fixture images.
- **Writes:** only the temporary copy — its database (a `-wal` file beside it while the server holds it open), its `_migrations` ledger as the pending migrations run, and its `images/`, where uploads and replacements land. Nothing under the dev app's directory is created, changed or removed, with one exception: a database the dev app left with a `-wal` file beside it is recovered in place when the copy step opens and closes it, as the app's next launch would do; a dev app running at the same time keeps its `-wal` file, since the copy step's connection is then not the last to close. The installed release app's directory is not read at all.
- **Writes (seeded mode):** only the temporary folder: the new database, its `_migrations` ledger, the seeded rows, and its `images/`, which starts with the seeded images.
- **Never:** nothing is committed, nothing reaches a paired device, and web-mode edits do not survive a server restart.

## Open points

None in the open-questions register.

Not yet registered; the first two are decided, the third is open:

- In web mode the pairing code is answered by the server but never shown: the pairing dialog shows it only after a peer requests it, and no peer exists in web mode. The settings rule above depends on it. Decided by Simon Schötz, 2026-10-20: the rule stands as narrowed to pairing mode opening without error; showing the code in web mode waits until a pairing test setup exists.
- The unreachable-server rule above cannot be observed by stopping the server and reloading: the server is Vite's own process, so a reload then fails at the connection and no page can show the Error Boundary; the message is reached only when a page is served without the server behind it. Decided by Simon Schötz, 2026-10-20: no hand test; the unit test on the message path is the check.
- The editor's "Open in browser" does not catch a refused link, so a web-mode scheme rejection, and the Tauri opener's own scope rejection, surface as an unhandled rejection. The link rules above depend on it.
