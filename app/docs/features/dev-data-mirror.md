# Dev data mirror

**Purpose.** `pnpm run dev` from `app/` replaces the Tauri dev app's database and images with a fresh copy of the installed release app's data before it launches — asking first when the dev app already holds data — so the dev app lists the same adventures, entities, sessions and images as the release app holds; web mode then serves a copy of that same dev data in the browser. The dev app keeps its own device identity and paired devices.

**Users.** The developer, who runs `pnpm run dev` and pairs the dev app only with test devices; the mirror is a development tool and never reaches a release build.

## How it works

Happy path:

1. `pnpm run dev` runs `node dev-data-server/runDevMirror.ts` and then `tauri dev --config src-tauri/tauri.dev.conf.json`, joined by `&&`. The entry reads the release identifier from `tauri.conf.json` and the dev identifier from `tauri.dev.conf.json`, so the release data is under `~/Library/Application Support/com.gm-tool/` and the dev data under `~/Library/Application Support/com.gm-tool.dev/`.
2. When the dev app already has a database, the entry asks `Replace the dev data with a copy of the installed app's data? [y/N]`. Only `y` or `yes` (any case) mirrors; Enter or any other answer keeps the dev data and starts the dev app on it. Without a terminal to ask in (the script started by a tool), the dev data is kept and a notice says so. A dev app without a database is mirrored without asking.
3. The mirror builds the copy in `.mirror-staging` inside the dev directory: the release database (a `-wal` file the release app left beside it is recovered in place) and the release `images/`. In the staged database it deletes the rows of the three preserved sets, then inserts the old dev database's rows of those sets for the columns both tables have.
4. It removes the old dev `gm_tool.db`, `gm_tool.db-wal`, `gm_tool.db-shm` and `images/`, moves the staged database and images in, removes the staging folder and prints one line naming the dev directory. `connectivity/` (the device key) and the `gm_tool.db.bak-*` backups are never touched.
5. `tauri dev` starts the dev app, which runs its pending migrations on the mirrored database as it does today. Edits made in the dev app survive the next `pnpm run dev` unless it is answered with `y`.

Failure:

- No installed app data, or a release directory that cannot be located (a machine that is not macOS): the entry prints a notice — naming `~/Library/Application Support/com.gm-tool/gm_tool.db`, or the macOS-only message — and exits 0, so the dev app starts on the data it already holds.
- Any other failure — a release database lacking one of the three preserved tables (the message names the table), a file that is not a database, the source and target directories being the same one: the entry prints the error and exits non-zero. The `&&` then keeps `tauri dev` from starting, and the old dev data is intact because nothing is swapped in before the copy is complete.

Where the user waits: at the prompt, when the dev app already holds data; then, before the dev app window opens, for the copy of the database and images.

## Data

- **Reads:** the release app's database and `images/` under `~/Library/Application Support/com.gm-tool/`, and the old dev database for the three preserved sets.
- **Writes:** the dev data directory only — its database and `images/` are replaced; a `-wal` file the release app left beside its database is recovered in place when the copy opens and closes it.
- **Never:** the release app's files are not changed (the `-wal` recovery excepted), and the dev `connectivity/` folder and `gm_tool.db.bak-*` files are not touched.
