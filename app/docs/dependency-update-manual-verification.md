## Owner decisions

These are choices, not tests. None can be settled by running something. Four were answered on 2026-10-01 and are kept here with their answers, since the reasoning is what a later reader needs; the rest are still open.

**Windows 7 — answered: not a concern.** tauri 2.12.0 drops Windows 7 support [research-rust-deps_6, as above], and the maintainer confirmed no Windows 7 target matters here, so this does not gate a release. Section 6's Windows items still apply, for the webview replacement rather than for the dropped platform.

**TypeScript 7 stays held at `~6.0.3`.** typescript-eslint throws `typescript-eslint does not support TS 7.0.` from a `versionMajor >= 7` guard that runs as its module loads, so a config importing it never reaches any file, and it declared `typescript: ">=4.8.4 <6.1.0"` at its latest 8.71.0 and at its 8.71.1-alpha.2 canary with no 9.x published [dependency-update_3: read `app/node_modules/typescript-eslint/dist/index.js:42-52` — observed the guard and the throw; ran `pnpm view typescript-eslint@8.71.0 peerDependencies` — observed that range] [research-typescript-7_3: ran `pnpm view typescript-eslint dist-tags` — observed latest 8.71.0 and canary 8.71.1-alpha.2] [research-typescript-7_4: ran `pnpm view typescript-eslint@8.71.1-alpha.2 peerDependencies` — observed the same range]. That is registry state on 2026-10-01, not a permanent property, so re-run `pnpm view typescript-eslint peerDependencies` before concluding it is still true. On a bare TypeScript 7 install `npx eslint .` lints nothing [research-typescript-7_6: ran `eslint .` in a throwaway probe with eslint 10.10.0, typescript-eslint 8.71.0 and typescript 7.0.2 — observed the throw instead of any lint output]; `npx vitest run` is expected to fail too, because `app/eslint-rules/__tests__/no-cycle-canary.test.js` loads the project's config through ESLint's programmatic API, but that was reasoned from the test's source rather than observed. TypeScript 7 itself reports zero errors on this codebase [research-typescript-7_23: ran `tsc --noEmit` at 7.0.2 over this repo's tsconfig — observed zero errors across an identical 2224-file program]. The interim workaround is a side-by-side alias where `tsc` runs TypeScript 7 while lint keeps a TypeScript 6 compiler; it also needs `onUnsupportedTypeScriptVersion: 'error'` in `app/eslint.config.js`, because `@typescript-eslint/typescript-estree` carries a second gate that compares the compiler actually loaded and does not throw unless its caller asks it to. Both guards are recorded in `.claude/knowledge/eslint.md`, verified at the versions this update installed.

**pnpm's release-age policy — answered: pinned.** `minimumReleaseAge: 1440` is now stated in both `pnpm-workspace.yaml` files, which changed no behaviour (that is pnpm's own default) but keeps the guard if the default moves. It is why the Tauri packages sit one patch behind latest: api/cli 2.12.1 and dialog 2.8.1 were published inside the window, and taking them made pnpm record a standing `minimumReleaseAgeExclude` bypass. Taking those two patches now needs only `pnpm up @tauri-apps/api@2.12.1 @tauri-apps/cli@2.12.1 @tauri-apps/plugin-dialog@2.8.1` from `app/` plus `cargo update -p tauri --precise 2.12.1` and `cargo update -p tauri-plugin-dialog --precise 2.8.1` from `app/src-tauri/`, since they are past the window by now. Note the guard covers npm only — cargo has no equivalent, so the Rust side relies on the same versions being chosen by hand. The behaviour is recorded in `.claude/knowledge/pnpm.md`.

**Whether to narrow `app/package.json`'s `engines.node` — still open, and now lower stakes.** It declares `^22.13.0 || >=23.4.0` while jsdom 30.1.1 requires `^22.22.2 || ^24.15.0 || >=26.0.0`, so the field claims support for Node versions on which installing would fail [dependency-update_4: read `app/package.json:9-11` and the installed `jsdom/package.json` `engines` field — observed those two ranges]. Since then Node has been pinned to the 22 line in a root `.nvmrc` and in the release workflow's `runtime: node@22`, which previously floated on `node@lts` and so could land CI on a different major than local. With both ends pinned, this field is advisory only and narrowing it is cosmetic honesty about the manifest.

**Whether to move to the Node 24 Active LTS line — open.** Everything here is verified on 22.23.2 only. nodejs.org lists 24 as the Active LTS line, 22 as the older LTS and 26 as Current; jsdom 30.1.1 accepts 24 from 24.15.0 onward. Moving means changing `.nvmrc` and the workflow together and re-running the full suite on 24 before trusting it, which is why the pin went to 22 rather than forward.

**Whether to clean up the dead `color` field on stored mentions.** 37 documents carry it, 120 values in total. The current `MentionNode` neither declares `color` in `SerializedMentionNode` nor writes it in `exportJSON`, so it is legacy data from an earlier schema, and Lexical 0.46 discards it exactly as 0.52 does [dependency-update_5: ran the same round-trip probe under both Lexical versions — observed 120 values dropped in both]. Nothing is broken by leaving it; the only cost is confusion when reading the database directly.
