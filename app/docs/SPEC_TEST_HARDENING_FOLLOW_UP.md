# Spec: Test-hardening follow-ups

- Sub-feature 1: Shared image test fixtures and tighter db assertions — one home for the image seed, image read and fake image commands; a null-acceptance guard for synced tables; the image `remove` test pins its `WHERE`
- Sub-feature 2: One peer-close timeout and accurate pairing comments — the 5-second wait for a peer's close becomes one crate constant; two pairing comments state what the code does
- Sub-feature 3: Services import form and sync-batch branch tests — `devicesService` imports the `_system` DB module by namespace; four `applyBatch` behaviours get a test each
- Sub-feature 4: Shared autosave-queue hook and pending-edit merges — `useAutosaveQueue` owns the queue holder and its unmount flush; pending edits merge like the cache does; deferred saves invalidate the list of the adventure they were scheduled for
- Sub-feature 5: Framing overlay saves through the data-access layer — the last framing edit survives closing the dialog, and opening the overlay writes nothing
- Sub-feature 6: Declared Node version for the db tests — `app/package.json` states the Node versions on which `node:sqlite` loads without a flag

Sub-feature 5 uses `useAutosaveQueue` from Sub-feature 4 and is implemented after it. Every other sub-feature is independent of the rest.

## Key Architectural Decisions

### One hook holds every autosave queue

`app/src/data-access-layer/useAutosaveQueue.ts` exports `useAutosaveQueue(merge, write)`, which creates the queue with `createAutosaveQueue(merge, write)` in `useState`'s lazy initializer and calls `flushAll()` from an unmount effect. The seven hooks with a debounced save (`useAdventure`, `useBaseEntity`, `useBaseEntityContentSections`, `useOwnDevice`, `useEncounter`, `useSessionSteps`, `useSession`) and `useUpdateImageFrame` call it instead of repeating that pair, so the flush-on-unmount wiring exists once and one test covers it; today a hook whose cleanup stopped calling `flushAll()` fails no test. The holder is never `useMemo`: every caller passes `write` as an inline closure that is new on each render, so a memo keyed on it would rebuild the queue, and the unmount effect would flush its pending edits, on every render, and React treats a memoized value as a cache it may discard [head-of-instructions_36: https://react.dev/reference/react/useMemo — as recorded in `.claude/knowledge/react.md`, entry "React may throw away a `useMemo` cached value…"]. Rule: `.claude/rules/src-react-hooks.md` — State is reserved for values with no synchronous source, the exception for an instance whose identity must persist across every render. The debounced-save bullet under `.claude/rules/src-data-access-layer.md` — Non-negotiable rules may still prescribe the per-hook `useState` plus unmount-effect pair; for the files this spec touches, the `useAutosaveQueue` call is the intended shape, and the rule change is recorded under CLAUDE.md impact.

### Pending edits merge the way the cache merges

A queue whose patch is a plain update object merges pending edits with `mergeUpdate` (`app/src/data-access-layer/mergeUpdate.ts`), which skips a key whose new value is `undefined`. `buildUpdateQuery` skips `undefined` values too [spec-writer_9: app/db/util/build-update-query.ts:17 — as of 529b24dd], and every hook whose patch is an update object already merges its optimistic cache update with `mergeUpdate` [spec-writer_10: grep mergeUpdate app/src/data-access-layer — found in the cache updates of useAdventure, useSession, useEncounter, useBaseEntity, useSessionSteps and useBaseEntityContentSections, as of 529b24dd]. The previous spread merge `(pending, patch) => ({ ...pending, ...patch })` let a later `undefined` erase an earlier pending value that the database then never received while the cache still showed it. No behaviour is lost: `undefined` never reached the database as a value. Passing `mergeUpdate` itself as the merge type-checks and lints for every plain update patch the hooks queue [spec-writer_7: ran `npx tsc --noEmit` and `npx eslint` from `app/` on a scratch module passing `mergeUpdate` as `createAutosaveQueue`'s merge for `UpdateAdventureData`, `UpdateSessionStepInput` and `UpdateBaseEntityContentSectionInput` — observed zero errors; scratch deleted].

### Scope fields travel with the pending edit and merge through one helper

A queued edit whose save must also know where the entity lives carries those fields beside `data`: `{ adventureId, data }` in `useSession` and `useEncounter`, `{ entityType, adventureId, data }` in `useBaseEntity`. The `write` callback passes them through `mutate()`'s variables, and `onSuccess` reads the list key's `adventureId` from those variables, never from the hook's `adventureId` parameter. `mutate` dispatches through one observer whose options, `onSuccess` included, are replaced by the latest committed render [debounce_32: app/node_modules/.pnpm/@tanstack+react-query@5.103.1_react@19.3.0/node_modules/@tanstack/react-query/build/modern/useMutation.js:180-188 — as recorded in `.claude/knowledge/tanstack-query.md`], so a closure read in `onSuccess` sees whichever adventure the reused route shows when the save finishes. Rule: `.claude/rules/src-data-access-layer.md` — Non-negotiable rules, the deferred-dispatch carve-out. One helper, `mergeScopedEdit` in `app/src/data-access-layer/mergeScopedEdit.ts`, merges these edits for all three hooks: every field except `data` is taken from the later edit, and `data` merges with `mergeUpdate` [spec-writer_8: ran `npx tsc --noEmit` and `npx eslint` from `app/` on a scratch module declaring `mergeScopedEdit = <Edit extends { data: object }>(pending: Edit, patch: Edit): Edit => ({ ...patch, data: mergeUpdate(pending.data, patch.data) })` and passing it as the merge for `{ adventureId: string; data: UpdateSessionInput }` and `{ entityType: BaseEntityType; adventureId: string; data: UpdateBaseEntityData }` — observed zero errors; scratch deleted].

### A latest-wins merge stays inline

`useOwnDevice` (`(_pending, name) => name`) and `useUpdateImageFrame` (`(_pending, frame) => frame`) each pass a merge that returns the later value. These stay as separate inline lambdas: each is a parameter projection with no logic of its own, and a shared export at the layer root would carry a mandatory helper test (`.claude/rules/src-unit-tests.md` — Testing Policy) that asserts only that a function returns its second argument, which catches no regression.

### The framing overlay saves through the data-access layer and saves only edits

`useUpdateImageFrame` owns the debounce and the flush through `useAutosaveQueue`, keyed by the image id at schedule time, and returns `updateFrame: (frame: ImageFrame) => void`. `app/src/CLAUDE.md` — TanStack Query pattern says components "own no async logic themselves", and the overlay's own timer lost any edit made less than 600 ms before the dialog closed. The overlay no longer writes the frame it opened with: that frame is either the stored one or the overlay's default `{ x: 50, y: 0, zoom: 1 }`, and the default equals the fallback `ImageById.css` applies when an image has no stored frame [spec-writer_11: app/src/components/ImageById/ImageById.css:5-9 — as of 529b24dd], so the write on open changed nothing visible. The save delay becomes the layer's `AUTOSAVE_DELAY_MS` (500 ms) instead of the overlay's 600 ms. `updateFrame` dispatches with `mutate`, never `mutateAsync`, so a flushed save that fails after unmount leaves no unhandled rejection [debounce_38: ran a scratch probe calling a first-render `mutate` from an unmount cleanup with `mutations.throwOnError: true` — observed `mutationFn`, hook `onSuccess` and `onSettled` running, per-call callbacks absent, and no unhandled rejection on failure — as recorded in `.claude/knowledge/tanstack-query.md`].

### Image test fixtures live in one support module and reach the test's database at call time

`app/db/__tests__/support/image-fixtures.ts` holds the fake answer to the Tauri image commands (now repeated in four db test files), the image-row seed (seven files) and the image-table read (two files) [spec-writer_17: grep 'const answerCommand', 'INSERT INTO images (id, file_extension, created_at, updated_at)' and 'SELECT \* FROM images' in app/db — found in the files Sub-feature 1 lists, as of 529b24dd]. A test imports the fixtures with `await import('@db/__tests__/support/image-fixtures')` inside the test body, or inside an async `beforeEach` after `vi.resetModules()`, because `.claude/rules/db-unit-tests.md` — Wiring a test that reaches `getDatabase()` requires a dynamic import for every `@db/...` module a test calls at runtime and allows only `import type` statically. The helpers also resolve `@db/database` with a dynamic `import()` when called, as the tests' own local helpers do today, so they reach the same freshly migrated database as the test's own dynamic imports; a static import of `@db/database` would bind another `database.ts` instance and so another database. The harness `app/db/__tests__/support/sqlite-test-database.ts` keeps its three exports.

### The null-acceptance guard reads the migrated database and parses the way sync does

The guard parses `{ [column]: null }` through `table.zodSchema.partial().safeParse(...)`, the expression `applyUpsert` applies to a peer row [review-decision_1: app/db/_sync/apply-upsert.ts:110 — as of 529b24dd]. It never indexes `table.zodSchema.shape`: on the registry's unparameterized `z.ZodObject` that index is typed `any` [spec-writer_5: app/node_modules/zod/v4/core/schemas.d.ts:694 — `export type $ZodLooseShape = Record<string, any>`, as recorded in `.claude/knowledge/zod.md`]. It reads nullability from the migrated database, not from `createTableSQL`, because older migrations can leave a column's nullability different from the current table definition.

### The peer-close wait is one crate constant

`connections.rs` and `pairing.rs` wait up to 5 seconds for the peer to close before closing locally, so a local close does not discard the last frame in flight. The two waits serve the same purpose, and the files already name their other timeouts (`CONNECTION_IDLE_TIMEOUT`, `VERDICT_TIMEOUT`). The shared value becomes `PEER_CLOSE_TIMEOUT` in `connectivity/mod.rs`, beside the module's other `pub(crate)` constants.

### The Node range is the set that loads `node:sqlite` without a flag

`engines.node` is `^22.13.0 || >=23.4.0`: `node:sqlite` needs no `--experimental-sqlite` flag from v22.13.0 on the 22.x line and from v23.4.0 on later lines [spec-writer_6: https://nodejs.org/api/sqlite.html — History entry "v23.4.0, v22.13.0: SQLite is no longer behind `--experimental-sqlite` but still experimental", as recorded in `.claude/knowledge/node.md`]. `>=22.13.0` alone would admit 23.0–23.3, which need the flag.

## CLAUDE.md impact

- `.claude/rules/src-data-access-layer.md` — Non-negotiable rules, the bullet beginning "A debounced save goes through `createAutosaveQueue`", prescribes that each hook hold the queue with `const [saveQueue] = useState(() => createAutosaveQueue<…>(merge, write));` plus an unmount effect calling `saveQueue.flushAll()`. After this branch, every data-access-layer hook with a debounced save calls `useAutosaveQueue(merge, write)` from `app/src/data-access-layer/useAutosaveQueue.ts`, which owns the holder and the flush; plain update patches merge with `mergeUpdate` (`app/src/data-access-layer/mergeUpdate.ts`), and patches carrying `entityType` or `adventureId` beside `data` merge with `mergeScopedEdit` (`app/src/data-access-layer/mergeScopedEdit.ts`). Consequence: a hook author following the bullet as written recreates the holder-and-flush pair and the spread merge that `useAutosaveQueue` and `mergeUpdate` replaced. [spec-writer_12: .claude/rules/src-data-access-layer.md, Non-negotiable rules — as of 529b24dd]
- `.claude/rules/src-data-access-layer.md` — Non-negotiable rules, the deferred-dispatch carve-out, tells a hook to pass "the identifier" through `mutate({ id, data })` when `mutationFn` would otherwise read it from the hook's closure. It says nothing about an identifier read in `onSuccess`. That gap let `useSession`, `useEncounter` and `useBaseEntity` (under `app/src/data-access-layer/`) invalidate `list(adventureId)` from the hook's render-time parameter after a deferred save. Consequence: a new hook with a deferred save can repeat that stale-list bug while complying with the rule as written. [spec-writer_13: app/src/data-access-layer/sessions/useSession.ts:32-39 — as of 529b24dd]
- `.claude/rules/src-unit-tests.md` — Testing Policy, the Required list, names helper and util functions, including "helper functions shared by several data-access-layer modules at the layer root". It names no data-access-layer hook and does not say whether a hook at the layer root (`useAutosaveQueue.ts`, `useDuplicateMutation.ts`) counts as such a helper. Consequence: a hook's deferred-dispatch logic has no owning test obligation. That logic is which id and `adventureId` a deferred save writes and invalidates, and which merge it passes to `useAutosaveQueue`, in `useSession`, `useEncounter`, `useBaseEntity` and `useUpdateImageFrame`. A regression that reads `adventureId` from the hook's closure in `onSuccess` again, or passes a spread merge instead of `mergeUpdate`, fails no test. `useDuplicateMutation.ts` has no test file. [spec-writer_14: .claude/rules/src-unit-tests.md:11 — as of 529b24dd] [spec-writer_15: `ls app/src/data-access-layer/__tests__/` — found only `createAutosaveQueue.test.ts` and `mergeUpdate.test.ts`, as of 529b24dd]
- `.claude/rules/db-unit-tests.md` names `app/db/__tests__/support/sqlite-test-database.ts` as the db tests' shared support and no other module. After this branch, `app/db/__tests__/support/image-fixtures.ts` holds `seedImage`, `readImages` and `answerImageCommand`, the shared image-row seed, image-table read and fake Tauri image-command answer, each resolving `@db/database` when called. Consequence: a new db test that needs an image row has no pointer to the shared seed and is likely to inline the `INSERT INTO images` statement again. [spec-writer_16: .claude/rules/db-unit-tests.md:7 — as of 529b24dd]
- `.claude/rules/db-unit-tests.md` — Wiring a test that reaches `getDatabase()` requires `await import(...)` inside the test for "every `@db/...` module the test calls at runtime". Its stated reason is that a static import binds another `db/database.ts` instance. `app/db/__tests__/support/image-fixtures.ts` is such a module, but it imports nothing from `@db/...` at module level: each helper resolves `@db/database` when called. So a static import of it would bind no second database, yet the rule's wording still requires the dynamic form. Consequence: every db test that uses a support helper adds a dynamic import to each test body, or turns its `beforeEach` async, to meet the wording rather than the reason. [spec-writer_18: .claude/rules/db-unit-tests.md, Wiring a test that reaches `getDatabase()`, last bullet — as of 529b24dd]
- The db tests need a Node release on which `node:sqlite` loads without a flag, the range recorded in `.claude/knowledge/node.md`. After this branch that requirement is declared in `app/package.json`'s `engines.node`. No `CLAUDE.md` or rule names it: `.claude/rules/db-unit-tests.md` says only that the tests run on "Node's bundled SQLite". Consequence: a reader of the instructions learns the requirement only from the manifest. No change is needed if the manifest is meant to be its only home. [spec-writer_16: .claude/rules/db-unit-tests.md:7 — as of 529b24dd]
