# Spec: Test Hardening

The database layer's tests stop asserting SQL text against a mocked `@tauri-apps/plugin-sql` and start running the real SQL against an in-memory SQLite database built by the app's own migration chain. Along the way this spec fixes the defects that the mock-based suite could not see: sync silently drops rows with empty text fields, deletions bounce between paired devices forever, a deleted row comes back when an older update arrives, image replacement deletes the old image before the new one is saved, and debounced saves lose or misroute the last half-second of edits. It also closes two pairing holes in the Rust backend — any device on the LAN can make itself trusted while the pairing dialog is open, and the attempt limit never stops a brute-force search of the 6-digit code — and makes "forget device" and closing the pairing dialog actually end their connections.

## Key Architectural Decisions

### Database tests run the real SQL against an in-memory SQLite built by the real migration chain

A db function's behavior lives in its SQL — its WHERE clause, ORDER BY, the foreign-key actions and sync triggers its statements set off. A test that mocks `plugin-sql` and asserts the SQL string it received cannot fail when that SQL is wrong, only when its text changes; that is the shared rules file's Best Practices & Code Quality rule beginning "A test earns its place by the regression it catches", whose in-process real-collaborator clause names a database. Node's built-in `node:sqlite` runs all twelve migrations unchanged through a thin adapter [spec-writer_1: ran `npx vitest run` on a scratch probe that mocked `@tauri-apps/plugin-sql` with a node:sqlite adapter and called `getDatabase()` — observed all 12 migrations applied, the `_migrations` ledger equal to `migrations.map(m => m.id)`, 15 tables and 24 `trg_sync_*` triggers], and a fresh chain takes about 4 ms after the first run in a worker [spec-writer_2: ran a timing probe — observed 3.2–4.3 ms per warm `getDatabase()` chain, 12–13 ms for the first]. No dependency is added. Tests of pure TypeScript — the query builders in `db/util/`, `validation.ts`, `defineTable`'s `updateSchema`, zod parsing of stored JSON — stay plain unit tests with no database.

### One harness module, imported only by db tests

`app/db/__tests__/support/sqlite-test-database.ts` is the single place that knows how to stand in for `@tauri-apps/plugin-sql`. It exports `openTestDatabase()`, `applyMigrationsBefore()` and the `TestDatabase` type, defined in SF2. Only test files under `app/db/**/__tests__/` import it; production code never does — it is test code, and `node:sqlite` exists only in Node, not in the Tauri webview. Vitest never collects it as a test because its file name does not match the default include pattern `**/*.{test,spec}.?(c|m)[jt]s?(x)` [spec-writer_3: app/node_modules/vitest/dist/chunks/defaults.D2ip7f-X.js:5]. It has its own test at `app/db/__tests__/support/__tests__/sqlite-test-database.test.ts`, because its placeholder translation, statement guard and failure injection are logic that would otherwise misbind values or break SF3's resume tests silently.

### The adapter matches plugin-sql 2.4.1's JavaScript surface and sqlx's binding rules

`TestDatabase` has `path`, `execute`, `select` and `close` with the shapes of `@tauri-apps/plugin-sql` 2.4.1's `Database` [spec-writer_4: app/node_modules/@tauri-apps/plugin-sql/dist-js/index.d.ts:1-13 (`QueryResult`), :21 (`path`), :88 (`execute`), :107 (`select`), :119 (`close`)], so it can be passed wherever the app expects a `Database` without a cast; no production code reads `execute`'s return value [spec-writer_5: grep `rowsAffected|lastInsertId` over app/db, app/services, app/src, app/domain, app/util — found only in `__tests__/` mocks]. Every method returns a promise and reports every failure — an SQLite error, the statement guard, an injected failure — as a rejection, as plugin-sql does. Four rules keep the adapter faithful to the app's sqlx connection:

- `$N` placeholders are rewritten to `?N` in every query the adapter prepares, which binds by number the way sqlx does (`.claude/knowledge/node.md` — "`node:sqlite` binds positional arguments to `?NNN` parameters by number, not by occurrence order"; `.claude/knowledge/sqlite.md` — "sqlx-sqlite binds a reused `$N` placeholder by parameter number, not by occurrence order"). No single-quoted SQL value inside a db query contains `$` followed by a digit, so the rewrite cannot corrupt a literal [spec-writer_6: ran a TypeScript AST scan over the string and template literals of the 123 non-test `.ts` files under app/db, extracting every single-quoted SQL value inside them — observed 74 such values and none containing `$` followed by a digit; the placeholder strings themselves, such as `'$1'` in build-create-query.ts:15, are the text the rewrite is meant to change].
- An `execute` without bind values runs through `DatabaseSync.exec()`, which runs every statement — migrations send multi-statement DDL this way. Every other query — `execute` with bind values, and every `select` — runs through `prepare()`, which silently compiles only the first statement (`.claude/knowledge/node.md` — "`DatabaseSync.prepare()` silently compiles only the first statement of a multi-statement string"), so the adapter rejects a prepared query that still contains a `;` after one trailing semicolon is trimmed. No current call trips this [spec-writer_7: ran a TypeScript AST scan over the 134 `execute`/`select` calls in non-test app/db files — observed no bind-carrying call and no `select` with more than one top-level statement; a runtime count over a chain plus CRUD run observed 0 of 71].
- Foreign keys are on, as they are under sqlx (`.claude/knowledge/sqlite.md` — "SQLite disables foreign key enforcement per connection by default, but sqlx enables it by default"); the adapter sets `PRAGMA foreign_keys = ON` explicitly rather than relying on node:sqlite's default.
- `select` copies each row into a plain object (`.claude/knowledge/node.md` — "`node:sqlite` returns rows with a null prototype"), so assertions behave as they would on the plain objects plugin-sql delivers over IPC.

### Test-file wiring under Vitest 5

A db test that reaches `getDatabase()` starts with the `// @vitest-environment node` docblock, mocks `@tauri-apps/plugin-sql` at the file's top level with a factory that imports the harness and returns `{ default: { load: () => Promise.resolve(openTestDatabase()) } }`, calls `vi.resetModules()` in `beforeEach`, and imports every `@db/...` module it calls at runtime — the unit under test, every module that creates parent rows or sets state such as `@db/pinned-order`'s `setPinnedOrder`, and `@db/database` when it reads the database directly — with `await import(...)` inside the test body; only `import type` stays static. A static import binds a different `database.ts` instance, and so a different database: a parent-row creator imported that way fails loudly on the foreign key, but a `setPinnedOrder` imported that way updates no row and lets a duplicate's "`pinned_order` is `null`" check pass vacuously. Each fresh `database.ts` instance loads a fresh database and runs the migration chain, so no test sees another's rows; this is the reset pattern `app/CLAUDE.md` — Testing requires for a function that reaches module-level singleton state through `getDatabase()`. The factory's `load` is not declared `async` because it awaits nothing, which `@typescript-eslint/require-await` (enabled by `strictTypeChecked`, app/eslint.config.js:12) would reject [spec-writer_8: ran `npx eslint` on a scratch db test with `load: async () => openTestDatabase()` — observed "Async method 'load' has no 'await' expression"; with `Promise.resolve(...)` lint and the test passed]. Four kinds of file use the harness without this wiring and say so where they are specified: the migration and registry tests (SF3, SF6), which call `openTestDatabase()` and run migrations directly; `ensure-column.test.ts` (SF7); the harness's own test (SF2); and `app/db/__tests__/init-database.test.ts` (SF3), which needs a spy on `Database.load` itself.

The mock sits at top level because Vitest 5 throws on a `vi.mock` or `vi.hoisted` call anywhere else (`.claude/knowledge/vitest.md` — "Vitest 5 throws at transform time on a `vi.mock` or `vi.hoisted` call that is not at the module's top level"), so no helper can install it. Vitest 5 also clears every mock's call history before each test (`.claude/knowledge/vitest.md` — "Vitest 5 clears every mock's call history before each test by default") and fails a `.resolves`/`.rejects` assertion that is not awaited [spec-writer_9: https://github.com/vitest-dev/vitest/blob/v5.0.1/docs/guide/migration/index.md, lines 349-362], so no db test asserts on mock history recorded outside its own body, and every such assertion is awaited.

Time is controlled wherever a test compares timestamps. A test that orders rows by a timestamp, or asserts that a timestamp is new, calls `vi.useFakeTimers({ toFake: ['Date'] })` and `vi.setSystemTime(...)` with a distinct instant before each write, and `vi.useRealTimers()` in `afterEach`: rows written in quick succession otherwise share a millisecond [spec-writer_10: ran a 50-iteration scratch probe — observed an update keeping its row's `updated_at` in 45 of 50 runs and a duplicate sharing its source's `created_at` in 44 of 50]. Timestamps SQLite writes itself (the sync triggers' `deleted_at`) come from SQLite's own clock, which fake timers do not reach, so any such value that two databases must agree on is overwritten with a fixed literal in the fixture. Invalid inputs that the TypeScript types forbid are passed through `as unknown as <the function's input type>`, as `db/base-entity-content-section/__tests__/update.test.ts:53` already does.

This wiring departs from `.claude/rules/db-unit-tests.md`: its Module registry reset section makes a static import with `afterEach(vi.resetModules)` the default for CRUD test files, and its Init path section requires `mockSelect.mockResolvedValue([])` in every file that reaches `getDatabase()`. Both presuppose the mocked `plugin-sql` this spec removes — with a real database there is no `mockSelect` to scope, and a static import would share one database across every test in the file. See CLAUDE.md impact.

### What a db test asserts

A db test asserts the rows a function leaves in the database and the values it returns, never the SQL text it sent and never the arguments of a mocked database call. A module's own `get`/`getAll` tests read back through that function; every other test reads back through `db.select(...)` on the database `getDatabase()` returns. `assertValidId`, `assertHasUpdateFields`, `buildCreateQuery`, `buildUpdateQuery`, `buildDuplicateQuery` and `generateDbTimestamps` are tested once, in `db/util/__tests__/`, and never again through each caller. Fixtures are chosen so a broken implementation fails: rows inserted out of order for ORDER BY, two parents for a WHERE filter, distinct source and target ids for a duplicate, `0` and `null` for "clears the field" and "falsy but defined", and non-default values set on a source row before the function is expected to copy or reset them. Every test named in an SF states the defect it catches. Four `get.ts` files carry an inline copy of `assertValidId`'s check instead of calling it [schema-inventory_141: app/db/adventure/get.ts:5-7] [schema-inventory_142: app/db/paired-device/get.ts:5-7] [schema-inventory_143: app/db/table-config/get.ts:10-12] [schema-inventory_144: app/db/image/get.ts:5-7, a weaker `!id` check]; SF4 and SF5 replace each with the shared call, which the shared rules file's Best Practices & Code Quality rule beginning "Reuse existing functions instead of duplicating logic" requires.

### Tests run SQLite 3.51.3; the app ships 3.46.0

The harness uses Node's bundled SQLite 3.51.3 (`.claude/knowledge/node.md`); the app bundles 3.46.0 (`.claude/knowledge/sqlite.md` — "This app's SQLite engine is the 3.46.0 amalgamation bundled by libsqlite3-sys 0.30.1"). Test setup code uses no SQL feature newer than 3.46.0. The two engine behaviors this spec's sync decisions rest on were checked on both engines: `.claude/knowledge/sqlite.md` — "Foreign key ON DELETE CASCADE fires the child table's DELETE triggers, before the parent's AFTER DELETE trigger", and `.claude/knowledge/sqlite.md` — "An `ON DELETE SET NULL` foreign-key action fires the child table's AFTER UPDATE trigger, before the parent's AFTER DELETE trigger, and changes no other column".

### Pairing trusts only a verdict this device asked for, and the attempt limit belongs to the session

Today a `CodeVerdict { accepted: true }` from any registered candidate makes it trusted even when this device never submitted a code to it, and the correct-code comparison runs before the failure count is read, so an endpoint over the limit still succeeds with a correct guess on a later connection [spec-writer_11: app/src-tauri/src/connectivity/pairing.rs:339-361 (verdict arm trusts regardless of `pending_verdict`), :305-318 (comparison before the counter), :320-325 (counter read only on the wrong-code path) — as of 51996f3f]. The counter is also keyed per endpoint id, and endpoint ids are free to generate, so a per-device limit does not bound guesses against the 6-digit code (`format!("{:06}", …)` at pairing.rs:68). After this spec: a verdict creates trust only while this device is waiting for it — the candidate's `pending_verdict` holds a sender whose receiver is still alive — and three wrong codes in total, from any device, lock the session: every later submission is rejected without comparing and the verifier emits `connectivity-pairing-failed` with reason `attempt limit reached`, which the dialog already shows as its error panel. Reopening the dialog starts a new session with a new code, because the session and its code are dropped when the last `exit_pairing_mode` runs (pairing.rs:93-103). The accepted cost: any device on the LAN can lock an open pairing session with three wrong codes, and the user then reopens the dialog. Both checks move into pure functions in `pairing.rs` so they can be unit-tested, per `app/src-tauri/CLAUDE.md` — Testing.

### A connection task ends when its map entry goes

`remove_peer` removes the peer's `ConnectivityData.connections` entry expecting the connection task to end, but `run_main_connection` keeps its own clone of the channel sender alive for its identity check (connections.rs:191, :301), and a tokio receiver returns `None` only when every sender is gone (`.claude/knowledge/tokio.md` — "A tokio mpsc receiver returns `None` only after every sender is dropped and its buffer is drained"). The forgotten peer's connection stays open, its frames keep reaching the frontend, and no disconnect event fires. `run_pairing_connection` does the same with `frame_sender` (pairing.rs:238-240, :388), so closing the pairing dialog leaves candidate connections open. After this spec neither task keeps a sender: the map entry owns the only one, and each task recognizes its own entry by `Connection::stable_id()` (`.claude/knowledge/iroh.md` — "iroh `Connection::stable_id()` stays fixed for the connection's lifetime and differs between connections open at the same time"). Because the receiver drains buffered messages first, an `unpair` envelope queued by `forgetDevice` just before `remove_trusted_peer` is still written; the main task then drops its streams, which finishes the send stream so the peer reads end-of-stream and closes, waits up to five seconds for that close — the same bounded wait the pairing verifier already uses at pairing.rs:374-377 so a local close does not truncate a frame in flight — closes the connection, and emits `connectivity-peer-disconnected` unless a newer connection has replaced its entry. A pairing candidate entry is replaced only by the connection both devices prefer — the one dialed by the smaller endpoint id, the rule `run_main_connection` already uses (connections.rs:193-209) — because once a replaced entry ends its connection, two devices keeping different connections would each close the other's and each drop the other as a candidate.

### Sync accepts `null` in nullable text columns

`applyUpsert` validates a peer row with `entry.zodSchema.partial()` (`db/_sync/apply-upsert.ts:109`). In `db/adventure/schema.ts`, `db/session/schema.ts` and `db/session-step/schema.ts`, nullable text columns carry `z.string().optional()`, which rejects `null` (`.claude/knowledge/zod.md` — "A `z.string().optional()` field rejects `null`, also after `ZodObject.partial()`"), and SQL `NULL` arrives as JSON `null` (`.claude/knowledge/tauri.md` — "tauri-plugin-sql decodes SQL `NULL` to JSON `null`"). So a new adventure (null `description`), a new session (null `name`, `description`, `summary`, `session_date`) or a step with a null `name` or `content` is skipped on every peer [spec-writer_13: ran a scratch probe applying rows made by `adventure.create()` and `session.create()` with a newer `updated_at` — observed `'skipped'`, zod reporting "expected string, received null"]. SF4 removes every `.optional()` from those three files, adding `.nullable()` where the field does not already have it; `app/db/CLAUDE.md` — Conventions ("No `zodSchema` field carries `.optional()`") already requires this of new code. These three files are grandfathered instances of that rule; `app/db/CLAUDE.md` — Grandfathering allows converting one as part of a deliberate, reviewed change, and this is one. The ripple was measured: 10 type errors, 9 in the mock fixtures of the three modules' test files that SF4 rewrites and one in `src/screens/adventures/components/ToAdventureBtn/ToAdventureBtn.tsx` [spec-writer_14: ran `npx tsc --noEmit` with the three files converted, then reverted them — observed 10 `error TS` lines: `db/adventure/__tests__/get-all.test.ts` 2, `get.test.ts` 1, `db/session/__tests__/get-all.test.ts` 2, `get.test.ts` 1, `db/session-step/__tests__/get-all-by-session.test.ts` 2, `get.test.ts` 1, and `ToAdventureBtn.tsx:21`]. The `image` and `paired-device` schema files keep their grandfathered `.optional()`: every nullable image column is `.nullable().optional()`, which accepts `null`, and `paired_devices` is not synced.

### A deletion is applied once

`applyDelete` on a row that no longer exists bumps the change counter and rewrites the tombstone every time (`db/_sync/apply-delete.ts:52-54`), and nothing marks a tombstone as received from a peer, so the receiving device pushes it back, the sender re-applies it, and the same deletion bounces between two connected devices on every three-second push [spec-writer_15: ran an in-process two-peer simulation over two node:sqlite databases routing `send_message` through a queue — observed the tombstone alternating `a→b @4, b→a @2, a→b @5, b→a @3, a→b @6, b→a @4` for all six ticks, and nine `table_config` seed tombstones bouncing the same way from the first handshake]. After this spec `applyDelete` with no local row reads the recorded tombstone for the row: when its `deleted_at` is equal to or later than the incoming one, it returns `'skipped'` and writes nothing; otherwise it bumps the counter and records the tombstone as today. A tombstone therefore keeps the latest deletion time, and a deletion echoes at most once before both devices hold the same tombstone. The tombstone lookup and the change-record id `<table>:<rowId>` live in one internal module, `db/_sync/tombstone.ts`, used by `applyDelete` and `applyUpsert` alike (SF6).

### An update older than a recorded deletion is skipped

`applyUpsert` compares an incoming row only with a local row; after a deletion there is none, so any later upsert re-inserts the row and its insert trigger clears the tombstone, whatever the timestamps [spec-writer_16: ran a scratch probe applying `applyDelete` with `deletedAt` 2030-01-01 and then `applyUpsert` of the same row with `updated_at` older, equal and newer — observed `'applied'` and the row back in all three cases; grep `_sync_changes` app/db/_sync/apply-upsert.ts — not found]. After this spec, for every synced table except `table_config`, `applyUpsert` reads the tombstone for the row before comparing with a local row: when its `deleted_at` is later than the incoming `updated_at`, the upsert returns `'skipped'`. A newer update brings the row back, and an equal timestamp keeps the row — the mirror of `applyDelete`, which skips a deletion when the local row's `updated_at` is equal to or later than it (`apply-delete.ts:44`). `table_config` is exempt: its rows are never deleted by the user; its tombstones come only from removing a duplicate row for the same `table_name` — a merge replacing one device's config id with the other's, stamped with the merging device's clock, or the dedup cleanup in `1787825905519_add_table_config_unique_index.ts:5-16`, which runs after the sync triggers exist — or from a peer relaying such a tombstone; and its merge already decides by comparing `updated_at` per `table_name` (apply-upsert.ts:66-74); a tombstone check there would keep an older config in the one case it changed [spec-writer_17: ran a scratch probe merging a config at 2001 and then applying an update for the replaced id at 2002 — observed the check returning `'skipped'` and keeping the 2001 config].

### Cascades and SET NULL write their own change records, and that is intended

Deleting a base entity records a tombstone for each of its content sections before the parent's [spec-writer_18: ran a scratch probe deleting a base entity with two sections through `db/base-entity/remove` — observed section tombstones at seq 20 and 21 and the base entity's at 22], and deleting an image rewrites the change record of each base entity or adventure that referenced it, with `image_id` now `NULL` and `updated_at` unchanged. Both are harmless with this spec's apply rules: `applyBatch` applies child deletions before parent deletions (`services/syncService.ts:189-197`), a re-sent child tombstone is skipped by the rule above, and a peer receiving the SET NULL row either skips it on the equal `updated_at` or applies it, while applying the image tombstone itself sets the same `NULL` through its own foreign key. The comment in `services/syncService.ts` that explains skipping a live change whose row is gone says the row's disappearance "travels with the parent tombstone"; SF6 corrects it to the actual mechanism — the row's own delete trigger, cascade included, has already rewritten that change as a tombstone with a later seq.

### Image replacement creates the new image before it removes the old one

`db/image/replace.ts` removes the old image and then creates the new one, so a new file that fails validation or copying leaves the entity's old image already deleted [spec-writer_19: app/db/image/replace.ts:9-10; app/db/image/create.ts:13-30 validates the extension and calls `save_image` after `replace` has already called `remove`]. After this spec `replace` calls `create` first and `remove` only after it succeeds. When `remove` then fails, the error propagates to `imageService.replaceImage`, which wraps it as it does today, and the caller does not point the entity at the new image, which stays unreferenced. Where `remove` fails matters: its `DELETE` (image/remove.ts:12) runs before `delete_image` (:15-18), so a failed file deletion leaves the old row already gone and the foreign key's `SET NULL` already applied — the entity ends up with no image. That sub-case is accepted; it is no worse than today, where the same failure has the same effect.

### Debounced saves go through one keyed queue that flushes on unmount

Seven data-access hooks debounce writes by 500 ms and discard the pending write when they unmount [spec-writer_20: app/src/data-access-layer/adventures/useAdventure.ts:23-29, encounters/useEncounter.ts:26-32, sessions/useSession.ts:26-32, base-entities/useBaseEntity.ts:30-36, base-entity-content-sections/useBaseEntityContentSections.ts:41-48, session-steps/useSessionSteps.ts:29-36, devices/useOwnDevice.ts:16-22 — each cleanup only clears its timer]. The four single-entity hooks also keep one pending object for whatever id is current, and the route component stays mounted when only a param changes (`.claude/knowledge/tanstack-router.md` — "A param change on the same route keeps the route component mounted unless `remountDeps` or `defaultRemountDeps` is set"; the app sets neither [spec-writer_21: grep `remountDeps|defaultRemountDeps` app/src — not found]), so an edit to entity B within 500 ms of an edit to entity A cancels A's timer and writes A's pending fields to B. SF8 replaces all seven with one helper, `createAutosaveQueue`, which keeps a separate pending patch and timer per key (the entity id) and exposes `flushAll()` for the unmount cleanup. Flushing through the hook's own `mutate` after unmount works (`.claude/knowledge/tanstack-query.md` — "A `mutate()` called after the component unmounts still runs `mutationFn` and the hook-level callbacks; per-call callbacks do not fire and errors are not rethrown"), and the queue can hold the first render's `mutate` (`.claude/knowledge/tanstack-query.md` — "`useMutation`'s returned `mutate`/`mutateAsync` always dispatches through one `MutationObserver` instance shared across every re-render of the same hook call site — never a per-render-frozen `mutationFn` closure"). The accepted consequence: a flushed save that fails after its screen unmounted is lost without a report. `mutate` swallows the rejection (`observer.mutate(...).catch(noop)`) [spec-writer_22: app/node_modules/.pnpm/@tanstack+react-query@5.103.1_react@19.3.0/node_modules/@tanstack/react-query/build/modern/useMutation.js:185-187], the `throwOnError: true` default (app/src/data-access-layer/queryClient.ts:11) reaches the Error Boundary only through a mounted component, and none of the seven hooks' debounced update mutations defines `onError` (the bulk-reorder mutations of `useBaseEntityContentSections` and `useSessionSteps` do, at :85 and :59, and are not flushed by the queue). A save that fails while the screen is still mounted behaves as today.

The queue lives at the data-access-layer root, `app/src/data-access-layer/createAutosaveQueue.ts`, beside `mergeUpdate.ts`, the other helper shared by several DAL modules, with its test in `data-access-layer/__tests__/` like `mergeUpdate.test.ts`. `app/src/CLAUDE.md` — Util vs. Helper Placement would put a generic helper with several consumers in `/src/util/`, but that directory belongs to the Frontend layer, which the spec format orders above the Data Access Layer (`app/docs/CLAUDE.md` — Spec Format Extension), and no DAL file imports `@/util` today [spec-writer_23: grep `@/util` app/src/data-access-layer — not found]; see CLAUDE.md impact. The shared 500 ms delay becomes `AUTOSAVE_DELAY_MS`, exported from the same file and exercised by its test.

### A latent SQL error in pinned order stays out of reach and untested
